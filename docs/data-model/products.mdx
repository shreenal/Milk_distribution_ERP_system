Products in the ERP are organized around a `master_product` row that carries brand, group, type, packaging attributes, and GST configuration. Rates are attached to a separate `(distributor, product)` join called `master_product_link`, not directly to the product.

## Master tables

```text
master_dairy            (e.g. "Amul", "Mother Dairy")
└── master_brand        (belongs to a dairy; has gatepass_date_policy)
    └── master_product_type   (optional; brand-scoped, unique (brand_id, name))
```

```text
master_product_group    (top-level SupplyCategory grouping: MILK | NON_MILK)
master_packaging_type   (packaging shape; used by product_tray_rule)
```

`master_product` composes these:

| Column | Purpose |
| --- | --- |
| `id` | PK |
| `code` | Unique product code |
| `brand_id` | FK → `master_brand` (required) |
| `product_group_id` | FK → `master_product_group` (required; carries `SupplyCategory`) |
| `product_type_id` | FK → `master_product_type` (nullable) |
| `packaging_type_id` | FK → `master_packaging_type` (nullable) |
| `packaging_size` | decimal(10,2) |
| `packaging_unit` | string (e.g. `L`, `ml`, `g`) |
| `is_gst_inclusive` | boolean controlling billing mode |
| `gst_percentage` | decimal(5,2) |
| `is_active` | soft delete |

Uniqueness: `@@unique([brand_id, product_group_id, product_type_id, packaging_type_id, packaging_size, packaging_unit])`.

There is no `default_rate`, `gst_rate`, `gst_inclusive`, or `product_category_id` column. The category is derived from `master_product_group.category`. GST fields are `is_gst_inclusive` and `gst_percentage`. There is no `master_product_variant`.

## master\_product\_link

The `(distributor, product)` join. Rates hang off this row, not `master_product`.

| Column | Purpose |
| --- | --- |
| `id` | PK |
| `distributor_id` | FK → `master_distributor` |
| `product_id` | FK → `master_product` |
| `is_active` | soft delete |

Uniqueness: `@@unique([distributor_id, product_id])`.

## Rate tables

Rates flow through two active tables (there is no global default):

### `master_client_rate_product`

Client-specific override on a `product_link`. Composite unique `(client_id, product_link_id, effective_from)`. Effective-dated via `effective_from`/`effective_to`.

### `distributor_product_rate`

Distributor's default rates on a `product_link` — carries both `purchase_rate` and `selling_rate`, effective-dated. Composite unique `(product_link_id, effective_from)`.

Rate resolution order at save time in the Orders module:

1. `master_client_rate_product` for `(client_id, product_link_id)` where active — client override.
2. `distributor_product_rate` for `product_link_id` where active — distributor default `selling_rate`.

Purchase rates come from `distributor_product_rate.purchase_rate` only, resolved on `product_link_id`.

## GST config

Two fields on `master_product` drive billing:

- **`is_gst_inclusive`** — when true, the entered selling rate already includes GST and the tax is backed out. When false, GST is added on top.
- **`gst_percentage`** — the percentage.

Both are read at morning save and snapshotted onto `order_sheet_items.final_gst_percentage` (and used to compute `final_taxable_amount`, `final_gst_amount`, `final_bill_amount`) so historical bills stay accurate even after config changes.

## Product tray rules

The link between products and trays lives in `product_tray_rule` — see [Trays data model](/data-model/trays) for the full matching hierarchy. Rules can be scoped at any level of the product hierarchy (specific product, product type, or brand-wide), and the module picks the most specific match.
