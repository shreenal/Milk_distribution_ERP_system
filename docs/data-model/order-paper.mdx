The `order_paper` table is the daily container that anchors every operational record in the system. Exactly one row exists per calendar `order_date`. Its `status` field drives the workflow state machine — every other module consults it before allowing writes.

## Schema

| Column | Type | Notes |
| --- | --- | --- |
| `id` | int, PK, autoincrement | Referenced by every child table |
| `order_date` | date, unique | The date the paper was generated for. Uniqueness lives on this column. |
| `sale_date` | date | The delivery date. `sale_date = order_date + 1` day when generated from `order_date`. |
| `status` | `OrderPaperStatus` enum | See below |
| `night_entry_submitted_at` | datetime, nullable | Set on `submit-night` |
| `morning_entry_submitted_at` | datetime, nullable | Set on `submit-morning` |
| `finalized_at` | datetime, nullable | Set on `finalize` (including re-finalize from `REOPENED`) |
| `reopened_at` | datetime, nullable | Set on `reopen`; not cleared on re-finalize |
| `reopen_reason` | string, nullable | Preserved verbatim; audit trail |
| `created_at`, `updated_at` | datetime | Standard timestamps |

## OrderPaperStatus enum

| Value | Meaning | Writes allowed |
| --- | --- | --- |
| `DRAFT` | Just generated; night entry in progress | orders (night), collections (night), vehicle-allocation |
| `NIGHT_SUBMITTED` | Night shift closed; delivery in progress | orders (morning), collections (morning), purchase, trays, dairy-tray |
| `MORNING_SUBMITTED` | Morning shift closed; awaiting admin review | collections (admin), cash-settlement, delivery-summary read |
| `FINALIZED` | Immutable | None; requires `reopen` |
| `REOPENED` | Finalized then reopened by admin | Same set as `MORNING_SUBMITTED`; refinalization needed |

Transitions are enforced by `WorkflowStateService.validateTransition()`. See [Paper States](/workflows/paper-states) for the state machine diagram.

## Child relationships

```text
order_paper
├── order_sheet[]              — one per active delivery group
├── purchase_paper?            — one per order_paper (order_paper_id is @unique)
├── vehicle_allocation_paper[] — up to two: one per (order_paper, delivery_session)
├── dairy_tray_paper?          — one per order_paper (order_paper_id is @unique)
├── distributor_transfer[]     — auto-generated on submit-morning
├── cash_direct_collection[]   — unique on (order_paper_id, employee_id)
└── cash_bank_deposit[]        — many per (order_paper, bank), no uniqueness
```

Cash route settlements are children of `order_sheet` (not `order_paper` directly). Cash route expenses are children of `cash_route_settlement`.

All direct children of `order_paper` use `onDelete: Cascade`, so deleting a paper removes every downstream record.

## Uniqueness constraints

- `@@unique(order_date)` — one paper per `order_date`, enforced at the DB level. There is no unique constraint on `sale_date`.
- Child tables that reference `order_paper` enforce their own composite uniqueness (e.g. `client_collection` on `(order_sheet_id, client_id, category)`, `vehicle_allocation_paper` on `(order_paper_id, delivery_session)`).
