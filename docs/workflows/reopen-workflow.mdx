The **reopen workflow** is the ERP's controlled way to correct a finalized paper. It exists because real-world deliveries produce mistakes: a delivered quantity was wrongly entered, a denomination count was off, a client's rate was fixed after the day was closed. Rather than editing rows silently, an Admin must reopen the paper with a documented reason, make the corrections, and re-finalize.

## When to reopen

Reopen a paper when:

- A delivered quantity or bill amount was recorded incorrectly and needs to be fixed.
- A cash denomination or bank deposit was entered wrong.
- A distributor transfer must be regenerated because supply rules or delivered quantities have been corrected.
- An admin-only collection remark or amount adjustment is needed.

Do **not** reopen for cosmetic issues (typos in remarks, unless they matter for audit), master data changes (new client, new rate — those go forward from the next paper), or reports that are missing lines (fix the report query instead of reopening).

## The reopen endpoint

`POST /papers/:paperId/reopen`

Request body:

```json
{ "reason": "Correction to Client 45's delivered qty on route 3; extra 2 crates were missed." }
```

The service:

- Rejects the request if the paper is not in `FINALIZED` (via `WorkflowStateService.validateTransition`).
- Updates `status` to `REOPENED`.
- Stamps `reopened_at` with the current timestamp.
- Sets `reopen_reason` to the exact string provided in the body.

Only Admins can call this endpoint (`@Roles('ADMIN')`).

<Warning>
  `PaperService.reopenPaperService` does **not** validate that `reason` is non-empty. An empty or whitespace-only `reason` is stored verbatim. Callers are expected to send a meaningful reason for the audit trail; the backend does not currently enforce this.
</Warning>

## What becomes editable

In `REOPENED`, the paper accepts writes on this set of modules (checked from `WorkflowStateService`):

- Morning-save on `order_sheet_items` (delivered qty, final rate, final amounts) — `canEditMorningEntries`.
- All three collection paths on `client_collection`: night save (`canEditNightCollections`), morning save (`canEditMorningCollections`), and admin save (`canAdminEditCollections`).
- Purchase entries — `canEditPurchases`.
- Client Trays (`canEditClientTrays`) and Dairy Trays (`canEditDairyTrays`).
- Vehicle Allocation — both `NIGHT` and `MORNING` sessions (`canEditVehicleAllocations` returns true for either session when the paper is `REOPENED`).
- Cash Settlement: **only `route-expenses`** (`canEditRouteExpenses` → `NIGHT_SUBMITTED`, `REOPENED`). Route denominations, direct collections, and bank deposits stay locked in `REOPENED` — their `canEdit…` helpers whitelist `NIGHT_SUBMITTED` only, so they cannot be re-entered from a reopened paper. This is deliberate: after reopen, cash settlement is treated as historical. The persisted denominations, direct collections, and bank deposits are preserved; expected cash is recalculated from the revised orders/collections; and the gap surfaces as **Reconciliation Difference** on the settlement summary instead of rewriting history.
- Distributor Transfer regeneration — `canEditDistributorTransfers` → `REOPENED` only.

Night saves for order items are **not** re-enabled by reopen. If a night quantity was wrong, correct the delivered quantity to match reality — the delivered quantity is what drives billing.

## Re-finalizing

`POST /papers/:paperId/finalize`

From `REOPENED`, the finalize endpoint transitions the paper straight back to `FINALIZED`. It does not require re-submitting night or morning entries because those submissions already happened; the timestamps `night_entry_submitted_at` and `morning_entry_submitted_at` are still set from the original run.

Re-finalize still runs the finalize readiness check (admin-only collection fields must be recorded on every sheet). It does **not** re-run the cash-settlement reconciliation that gates the first `MORNING_SUBMITTED → FINALIZED` transition, because cash settlement is treated as historical after reopen.

The service stamps `finalized_at` again. `reopened_at` and `reopen_reason` are **not** cleared — they remain as a permanent record of the correction.

## Audit trail

After a reopen and re-finalize, the paper's timestamp fields look like:

- `night_entry_submitted_at` — original night submit (untouched).
- `morning_entry_submitted_at` — original morning submit (untouched).
- `finalized_at` — the _most recent_ finalization; overwritten each time.
- `reopened_at` — the _most recent_ reopen; overwritten each time.
- `reopen_reason` — the _most recent_ reopen reason; overwritten each time.

<Warning>
  The system currently records only the most recent reopen event. If a paper is reopened, re-finalized, and reopened again, the earlier reason is overwritten. If your business needs multi-reopen history, add an audit table before relying on `reopen_reason` for compliance.
</Warning>

## Diagram

```text
Admin → POST /papers/:paperId/reopen   { reason: "..." }
              │
              ▼
        status = REOPENED, reopen_reason = "..."

Employee/Admin → correct data via the usual save endpoints
                  (orders morning, collections, purchase, trays, cash settlement)

Employee/Admin → POST /distributor-transfer/:paperId/generate  (if needed)

Admin → POST /papers/:paperId/finalize
              │
              ▼
        status = FINALIZED, finalized_at updated
        reopened_at and reopen_reason preserved
```
