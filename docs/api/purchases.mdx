The Purchases API records inbound stock. Each morning (and evening for two-session flows), vehicles pull up to a dairy, load product, and receive a gate pass. Those loads are captured as `purchase_entry` rows attached to a `purchase_paper` scoped to the day's `order_paper` and a delivery session (`NIGHT` or `MORNING`). Purchase amounts feed the distributor's payables and appear on the daily P&L.

`EMPLOYEE` (and above via role hierarchy) can call these endpoints. The paper's workflow state determines whether writes succeed. The controller lives at `@Controller('purchases')` with `:paperId` as the leading segment.

---

## GET /purchases/:paperId

### Purpose

Returns the purchase page payload for the paper: the `purchase_paper` (if any), all `purchase_entry` rows, plus vehicle, distributor, and product metadata needed to render the grid.

### Path parameters

<ParamField path="paperId" type="number" required>
  Order paper primary key.
</ParamField>

### Response

Returns HTTP **200** with the shape returned by `PurchaseService.getPurchases`, including entries with `id`, `vehicle_id`, `product_id`, `product_link_id`, `distributor_id`, `delivery_session`, `category`, `purchased_qty`, `purchase_rate`, `purchase_amount`, and `gatepass_date`.

---

## POST /purchases/:paperId

### Purpose

Upserts purchase entries for the paper. Each entry is scoped by `(vehicleId, deliverySession, distributorId, category, productId)`; the uniqueness constraint on the row is `(purchase_paper_id, delivery_session, vehicle_id, product_link_id)` where `product_link_id` is resolved from `(distributorId, productId)`.

### Access control

`EMPLOYEE`. Editable when `WorkflowStateService.canEditPurchases(status)` returns true — that is, when the paper is in `NIGHT_SUBMITTED` or `REOPENED`.

### Request body

`SavePurchaseDto`:

<ParamField body="entries" type="array" required>
  Array of purchase entries. Each entry:
</ParamField>

<ParamField body="entries[].deliverySession" type="string" required>
  `NIGHT` or `MORNING`.
</ParamField>

<ParamField body="entries[].category" type="string" required>
  `MILK` or `NON_MILK`.
</ParamField>

<ParamField body="acknowledgements" type="array">
  Optional array of variance acknowledgements. One entry per purchase line whose `purchasedQty` differs from the corresponding vehicle allocation. Each acknowledgement:

  - `vehicleId`, `deliverySession`, `distributorId`, `category`, `productId` — must match a purchase entry in the same request.
  - `reason` — one of `SHORT_SUPPLY`, `EXCESS_SUPPLY`, `DAMAGED_PRODUCT`, `QUALITY_REJECTION`, `MANUAL_ADJUSTMENT`, `OTHER`.
  - `remarks` — optional free-text; required by validation for reasons that need it.
</ParamField>

#### Example request

```json
POST /purchases/128
Authorization: Bearer <token>
Content-Type: application/json

{
  "entries": [
    {
      "vehicleId": 3,
      "deliverySession": "MORNING",
      "distributorId": 5,
      "category": "MILK",
      "productId": 7,
      "purchasedQty": 38
    }
  ],
  "acknowledgements": [
    {
      "vehicleId": 3,
      "deliverySession": "MORNING",
      "distributorId": 5,
      "category": "MILK",
      "productId": 7,
      "reason": "SHORT_SUPPLY",
      "remarks": "Dairy short-supplied 2L"
    }
  ]
}
```

### Behavior

- `purchase_paper` is created on demand for the `order_paper` (unique on `order_paper_id`) if it does not exist.
- `product_link_id` is resolved from `(distributorId, productId)` via `master_product_link`; the entry is rejected if no active link exists.
- `purchase_rate` is resolved from `distributor_product_rate` on that `product_link_id`, active at the paper's date.
- `purchase_amount = purchasedQty × purchase_rate`.
- `gatepass_date` is derived from `master_brand.gatepass_date_policy` (`SAME_DAY` → `sale_date`; `PREVIOUS_DAY` → `sale_date − 1`).
- Every entry is compared against its planned `vehicle_allocation.allocated_qty` for the same `(vehicle, distributor, category, product, deliverySession)`. If the two differ, the request must carry a matching entry in `acknowledgements`; otherwise the save is rejected. Conversely, an acknowledgement without an actual variance is also rejected.
- Acknowledgements are upserted into `purchase_variance_acknowledgement` (unique per `purchase_entry_id`), recording `reason`, optional `remarks`, and the authenticated user in `acknowledged_by`.

### Validation and errors

| Scenario | HTTP status | Detail |
| --- | --- | --- |
| Paper not in `NIGHT_SUBMITTED` or `REOPENED` | `400 Bad Request` | Purchases locked in other states |
| No active `master_product_link` for `(distributorId, productId)` | `400 Bad Request` | Cannot resolve product link |
| No active `distributor_product_rate` for the product link | `400 Bad Request` | Rate resolution failed |
| `deliverySession` not `NIGHT`/`MORNING`, `category` not `MILK`/`NON_MILK`, or `reason` not a valid `PurchaseVarianceReason` | `400 Bad Request` | DTO enum validation |
| `purchasedQty` exceeds `allocated_qty` for the line | `400 Bad Request` | `Purchased quantity exceeds allocated quantity` |
| Variance exists but no matching acknowledgement supplied | `400 Bad Request` | `Purchase variance must be acknowledged before saving` |
| Acknowledgement supplied but no variance on that line | `400 Bad Request` | `Variance acknowledgement is not allowed when there is no variance` |
| Duplicate acknowledgement for the same line | `400 Bad Request` | `Duplicate variance acknowledgement detected` |
