The Papers API is the backbone of the daily operational cycle. Every order, collection, purchase, tray movement, and cash reconciliation is anchored to a single `order_paper` row identified by its `paperId`. The endpoints below generate a new paper for a given date, retrieve existing papers, and drive the paper through its five workflow states: `DRAFT` → `NIGHT_SUBMITTED` → `MORNING_SUBMITTED` → `FINALIZED` (with an optional `REOPENED` branch for corrections).

All endpoints require an `Authorization: Bearer <token>` header. The token's `role` claim determines who can call which mutating endpoint — read endpoints are open to `EMPLOYEE` and `ADMIN`, while `finalize` and `reopen` are restricted to `ADMIN`.

---

## POST /papers

### Purpose

Generates the daily order paper for a given date. Creates the top-level `order_paper` row along with all child `order_sheet` rows (one per delivery group) and pre-populates each sheet with the eligible clients based on supply rules in effect on that date.

### When it is called

Called once per day by the night-shift operator, typically the evening before the delivery date. If a paper already exists for the requested date, the existing paper is returned as-is — no error is raised.

### Request body

<ParamField body="date" type="string" required>
  The sale date in `YYYY-MM-DD` format. Represents the day the goods will be delivered.
</ParamField>

#### Example request

```json
POST /papers
Authorization: Bearer <token>
Content-Type: application/json

{
  "date": "2026-07-29"
}
```

### Response

Returns HTTP **201** (Nest default for `@Post`) with the paper record. When a new paper is created, all delivery-group `order_sheet` rows are generated alongside it. When a paper already exists for the date, the existing record is returned unchanged.

<ResponseField name="id" type="number">
  The `paperId` used by every other endpoint.
</ResponseField>

<ResponseField name="sale_date" type="string">
  ISO date of the paper.
</ResponseField>

<ResponseField name="status" type="string">
  Always `DRAFT` immediately after creation.
</ResponseField>

<ResponseField name="order_sheet" type="array">
  One entry per delivery group participating on this date. Present in the aggregate returned by `GET /papers/:paperId`; the create response contains at minimum the paper row itself.
</ResponseField>

### Validation and errors

| Scenario | HTTP status | Detail |
| --- | --- | --- |
| `date` missing | `400 Bad Request` | `Required field "date" is missing` |
| `date` malformed | `400 Bad Request` | `Invalid date format` |
| `date` is in the past | `400 Bad Request` | `Cannot perform operations on past dates` |
| `date` more than 30 days ahead | `400 Bad Request` | `Cannot generate paper more than 30 days ahead` |
| No active groups configured | `400 Bad Request` | `No active groups found to generate sheets` |
| Caller is not `EMPLOYEE` or `ADMIN` | `403 Forbidden` | Role check failure |

## GET /papers/today

### Purpose

Convenience endpoint that returns the paper whose `sale_date` matches today's server date. If no paper exists for today, the service falls back to returning the most recent paper on record. Used by the client on app start to jump straight to a paper without needing to know its ID.

### Request

No body or query parameters. Requires a valid bearer token.

### Response

Returns HTTP **200** with a wrapper object:

```json
{
  "type": "TODAY" | "LATEST",
  "paper": { /* full paper aggregate */ }
}
```

- `type: "TODAY"` — a paper exists for the current date.
- `type: "LATEST"` — no paper for today; the most recent historical paper is returned.

### Validation and errors

| Scenario | HTTP status | Detail |
| --- | --- | --- |
| No papers exist in the system at all | `400 Bad Request` | `No papers found in system` |

## GET /papers

### Purpose

Lists papers, optionally filtered by date. Used by admins to page through historical papers or to look up a specific date.

### Query parameters

<ParamField query="date" type="string">
  Optional. If provided, returns the single paper matching that exact date (as an object, not an array). Without this parameter, returns a chronological array of all papers.
</ParamField>

#### Example request

```http
GET /papers?date=2026-07-15
Authorization: Bearer <token>
```

### Response

Returns HTTP **200**. When `date` is omitted, the response is an array of paper records. When `date` is provided, the response is a single paper record.

### Validation and errors

| Scenario | HTTP status | Detail |
| --- | --- | --- |
| `date` malformed | `400 Bad Request` | `Invalid date format` |
| `date` provided but no paper on that date | `400 Bad Request` | `Order paper not found` |

## GET /papers/:paperId

### Purpose

Retrieves a complete paper by ID, including all order sheets, sheet items, and child collections. This is the primary read endpoint used by every screen in the app.

### Path parameters

<ParamField path="paperId" type="number" required>
  Numeric primary key of the paper.
</ParamField>

### Response

Returns the full paper aggregate. See [Order Paper data model](/data-model/order-paper) for the exact shape.

### Validation and errors

| Scenario | HTTP status | Detail |
| --- | --- | --- |
| `paperId` not a positive integer | `400 Bad Request` | Nest `ParseIntPipe` failure |
| No paper with that id | `400 Bad Request` | `Order paper not found` (the codebase throws `BadRequestException`, not `NotFoundException` — see [Error Handling](/architecture/error-handling)) |

## POST /papers/:paperId/submit-night

### Purpose

Transitions the paper from `DRAFT` to `NIGHT_SUBMITTED`. Called once the night-shift operator has finished entering ordered quantities, night-side collections, and vehicle allocations. After this call, night-shift data becomes read-only and the morning workflow unlocks.

### Behavior

- Validates that all required night-side entries exist for every sheet.
- Runs the workflow state machine; rejects the call if the paper is not currently in `DRAFT`.
- Emits no external side effects — purely a state change.

### Validation and errors

| Scenario | HTTP status | Detail |
| --- | --- | --- |
| Paper not in `DRAFT` | `400 Bad Request` | `Cannot transition from <status> to NIGHT_SUBMITTED` |
| Missing required night entries | `400 Bad Request` | `Night entry incomplete for sheet "<groupName>"` (or the specific validator message) |

---

## POST /papers/:paperId/submit-morning

### Purpose

Transitions the paper from `NIGHT_SUBMITTED` to `MORNING_SUBMITTED`. Called once the morning-shift operator has recorded delivered quantities, purchase entries, tray movements, and morning-side collections.

### Side effects

On success, this endpoint auto-generates the `distributor_transfer` records that reconcile stock between distributors when a client's `owner_distributor` differs from the supplying distributor. See [Distributor Transfer workflow](/workflows/distributor-transfer) for the full rules.

### Validation and errors

| Scenario | HTTP status | Detail |
| --- | --- | --- |
| Paper not in `NIGHT_SUBMITTED` (or `REOPENED`) | `400 Bad Request` | `Cannot transition from <status> to MORNING_SUBMITTED` |
| Missing morning entries | `400 Bad Request` | Message from the relevant readiness validator |

---

## POST /papers/:paperId/finalize

### Purpose

Transitions the paper from `MORNING_SUBMITTED` to `FINALIZED`. Once finalized, no user (including admins) can edit any child record without going through the reopen workflow.

### Access control

`ADMIN` role only. `EMPLOYEE` tokens receive `403 Forbidden`.

### Validation and errors

| Scenario | HTTP status | Detail |
| --- | --- | --- |
| Caller not `ADMIN` | `403 Forbidden` | Role check failure |
| Paper not in `MORNING_SUBMITTED` | `400 Bad Request` | `Cannot transition from <status> to FINALIZED` |
| Reopened paper without morning resubmit | `400 Bad Request` | `After reopening from <previousStatus>, you must resubmit morning entry before finalizing` |
| Admin-side collections incomplete | `400 Bad Request` | Message from the finalize readiness validator |

---

## POST /papers/:paperId/reopen

### Purpose

Transitions a `FINALIZED` paper to `REOPENED` so an admin can correct data. The request body carries a `reason` string that is stored verbatim on the paper for audit.

### Request body

<ParamField body="reason" type="string">
  Free-text explanation. Persisted verbatim on the paper. Callers are expected to send a meaningful reason. `PaperService.reopenPaperService` does not enforce a non-empty check, so an empty or whitespace-only value is accepted and stored as-is.
</ParamField>

### Access control

`ADMIN` role only.

### Validation and errors

| Scenario | HTTP status | Detail |
| --- | --- | --- |
| Caller not `ADMIN` | `403 Forbidden` | Role check failure |
| Paper not in `FINALIZED` | `400 Bad Request` | `Cannot transition from <status> to REOPENED` |

After reopen, re-run `submit-morning` and `finalize` to close the paper again. See [Reopen Workflow](/workflows/reopen-workflow) for details.
