Every mutating request in the ERP API passes through the same seven-stage pipeline. Understanding it makes the codebase far easier to trace, because each layer has one clear job.

## The seven stages

```text
┌─────────────────────────────────────────────────────────────────┐
│  1. HTTPS termination                                           │
│  2. Global ValidationPipe (whitelist + transform)               │
│  3. JwtAuthGuard  →  attaches request.user                      │
│  4. RolesGuard    →  checks @Roles(...)                         │
│  5. Controller    →  parses params, delegates to service        │
│  6. Service       →  runs business logic inside prisma.$tx      │
│  7. Nest's default exception handling (only on error)           │
└─────────────────────────────────────────────────────────────────┘
```

## Stage 1 — HTTPS termination

Handled by whatever reverse proxy or platform load-balancer sits in front of the Node process. The application itself listens on `PORT` (default 3000) over plain HTTP.

## Stage 2 — Global ValidationPipe

Registered in `main.ts`:

```typescript
app.useGlobalPipes(
  new ValidationPipe({ whitelist: true, transform: true }),
);
```

- **`whitelist: true`** strips any property from the request body that isn't declared on the DTO. Prevents accidental overwrites of protected fields.
- **`transform: true`** converts route params and query strings to their declared TypeScript types (`ParseIntPipe` on `paperId`, string-to-Date coercion for query dates).

Failures raise `BadRequestException` (`400`) before the controller ever runs.

## Stage 3 — JwtAuthGuard

Reads the `Authorization: Bearer <token>` header, verifies the JWT signature with the signing key configured in `JwtStrategy` (read from `process.env.SECRET` via `ConfigService`), and rejects expired or malformed tokens with `401`. On success it attaches the decoded payload — `{ id, username, role }` returned from `JwtStrategy.validate` — to `request.user`.

## Stage 4 — RolesGuard

Reads the `@Roles(...)` decorator on the handler and compares against `request.user.role`. Mismatch → `403 Forbidden`. See [Authentication](/architecture/authentication).

## Stage 5 — Controller

The controller has three responsibilities and only three:

1. Parse and coerce path/query/body parameters.
2. Call the corresponding service method.
3. Return the service's result.

Controllers contain **no business logic**. Example:

```typescript
@Post(':paperId/submit-morning')
@Roles('EMPLOYEE')
async submitMorningEntry(
  @Param('paperId', ParseIntPipe) paperId: number,
) {
  return this.paperService.submitMorningEntryService(paperId);
}
```

## Stage 6 — Service and validation

The service is where all rules live. A typical mutating service method:

1. Loads the affected paper via the repository.
2. Delegates to a validation service (`services/<module>-validation.service.ts` in most transaction modules; at the module root for `distributor-transfer`) to check workflow state, referential integrity, and business rules.
3. Opens a Prisma `$transaction` to perform the mutation atomically.
4. Returns the updated aggregate.

The `WorkflowStateService` is injected almost universally to answer per-module `canEdit*` questions (for example `canEditNightEntries(paper.status)` or `canEditVehicleAllocations(paper.status, session)`). No module implements state gating independently. Shared calculators from `src/common/calculators/` (`CashSettlementCalculationService`, `PurchaseVarianceCalculator`, `TrayCalculationService`) are injected where the same math is needed by more than one module (for example the cash-settlement service and the paper readiness check both consume denomination totals).

## Stage 7 — Nest's default exception handling

There is no custom global `ExceptionFilter` registered. The file `src/common/filters/http-exception.filter.ts` exists in the tree but is empty and is not wired into `main.ts` or through `APP_FILTER`. Every `HttpException` (or subclass) thrown anywhere in the request lifecycle is caught by Nest's built-in exception layer and converted into the standard error envelope:

```json
{
  "statusCode": 400,
  "message": "Cannot edit night entries when paper is NIGHT_SUBMITTED. Allowed statuses: DRAFT, REOPENED",
  "error": "Bad Request"
}
```

There is no `path` or `timestamp` field because no custom filter injects them.

Uncaught, non-`HttpException` errors (e.g. database connection failures) fall through to Nest's default `500 Internal Server Error` with `"Internal server error"` as the message.

## Where the guards don't run

The single `POST /auth/login` route omits `@UseGuards(JwtAuthGuard)` because a caller cannot yet have a token. `ValidationPipe` still runs, and Nest's default exception handling still formats any errors.
