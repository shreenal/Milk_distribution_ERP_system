The Milk Distribution ERP backend is a NestJS application written in TypeScript. It exposes a REST API consumed by an Electron desktop client (React \+ Vite) running on distributor workstations. Data is persisted in PostgreSQL through the Prisma ORM. Every HTTP route is protected by JWT authentication and a role-based access control layer.

## Technology Stack

| Layer | Technology | Rationale |
| --- | --- | --- |
| API framework | NestJS (TypeScript) | Opinionated module structure; built-in DI, guards, pipes |
| ORM | Prisma | Type-safe query builder; schema-first migrations |
| Database | PostgreSQL | ACID transactions; well-suited for financial record-keeping |
| Authentication | JWT (Bearer) \+ Passport.js | Stateless; straightforward to validate at the edge |
| Desktop client | Electron \+ React \+ Vite | Native OS integration for offline-capable distribution operations |
| Validation | NestJS `ValidationPipe` (class-validator) | DTO-level input sanitisation before business logic runs |

## Project Structure

The `src/modules` tree is split into two top-level buckets: **`masters/`** (CRUD-style reference data grouped by domain area) and **`transactions/`** (the day-to-day operational workflows anchored on the daily paper). All feature modules are registered from `AppModule` in `src/app.module.ts`.

## Internal Module Layout

Most feature modules follow the same internal layer pattern:

```text
<module>/
├── <module>.controller.ts      # HTTP routes, guards, param parsing
├── <module>.service.ts         # Business logic, orchestration
├── <module>.repository.ts      # Prisma queries
├── <module>-validation.service.ts  # Business-rule validation
├── <module>.builder.ts         # Response/grid construction
├── <module>.constants.ts       # Error messages, config values
├── <module>.module.ts          # NestJS module definition
└── dto/                        # Request body shapes (class-validator)
```

### Master modules

Every module under `src/modules/masters/*` follows a strict CRUD-only layout: `<module>.controller.ts`, `<module>.service.ts`, `<module>.repository.ts`, `<module>.module.ts`, and `dto/create-*.dto.ts` \+ `dto/update-*.dto.ts`. Masters have no `*-validation.service.ts`, no `*.builder.ts`, and no `*.constants.ts` — with two exceptions:

- `masters/clients/clients/` ships `clients.constants.ts` for the `CLI` code prefix and code length.
- `masters/products/products/` ships `products.constants.ts` for `MAX_GST_PERCENTAGE`, `PRODUCT_CODE_PREFIX`, and `PRODUCT_CODE_LENGTH`.

Two masters use a non-plural filename convention:

- `masters/distribution/distributors/` uses `distributor.controller.ts` / `distributor.service.ts` / `distributor.repository.ts` / `distributor.module.ts`.
- `masters/products/product-groups/` uses `product-group.controller.ts` / `product-group.service.ts` / `product-group.repository.ts` / `product-group.module.ts`.
- `masters/products/packaging-types/` uses `packaging-type.module.ts` (but the controller, service, and repository files are the plural `packaging-types.*`).

### Transaction modules

Transaction modules under `src/modules/transactions/*` follow the fuller pattern with these concrete deviations:

- `auth/` — has no builder, no `*-validation.service.ts`, no constants. It ships `auth.controller.ts`, `auth.service.ts`, `auth.repository.ts` (currently commented out; `AuthService` injects `UsersRepository` from the users master), `auth.module.ts`, `auth.guard.ts`, `jwt.strategy.ts`, `roles.guard.ts`, `roles.decorator.ts`, and `dto/login.dto.ts`.
- `paper/` — has no builder. It ships `paper.repository.spec.ts` (test file); there is no `paper.service.spec.ts`.
- `delivery-summary/` — no validation service, no `dto/` folder (read-only).
- `distributor-transfer/` — no `dto/` folder.
- `orders/` — uses `order.billing-builder.ts` (not `orders.builder.ts`).
- `trays/` — uses `tray.billing-builder.ts` (not `trays.builder.ts`).
- `workflow/` — pure state-machine module. Files: `workflow-state.service.ts`, `workflow.builder.ts`, `workflow.module.ts`, plus `constants/workflow-status.constants.ts`, `guards/workflow-status.guard.ts`, and `types/workflow.types.ts`. No controller or repository.

This separation ensures that HTTP concerns stay in the controller, database concerns stay in the repository, and all domain rules live exclusively in the service and validation service.

## Shared Cross-Cutting Services

Two services are injected into almost every feature module:

- **`WorkflowStateService`** — provides a full set of `canEdit*` boolean methods (`canEditNightEntries`, `canEditMorningEntries`, `canEditNightCollections`, `canEditMorningCollections`, `canEditTrays`, `canEditEmployeeCollections`, `canAdminEditCollections`, `canEditVehicleAllocations`, `canEditPurchases`, `canEditRouteExpenses`, `canEditRouteDenominations`, `canEditDirectCollections`, `canEditBankDeposits`, `canEditDairyTrayTracking`, `canEditDistributorTransfers`, `canFinalize`) plus `validateTransition` for the paper status machine. No module enforces workflow rules independently.
- **`PrismaService`** — the singleton Prisma client (from `src/prisma/prisma.service.ts`); used directly in services for `$transaction` calls and indirectly via repositories for single queries. A separate standalone client in `src/lib/prisma.ts` is used by scripts that need a Prisma instance outside the Nest container.

## Application Bootstrap

`main.ts` creates the NestJS application with a global `ValidationPipe` configured for `whitelist: true` (strips unknown properties) and `transform: true` (auto-converts route params to their declared types), plus CORS enabled for the Electron/Vite client origin:

```typescript
const app = await NestFactory.create(AppModule);
app.useGlobalPipes(
  new ValidationPipe({ whitelist: true, transform: true }),
);
app.enableCors({
  origin: 'http://localhost:5173',
  credentials: true,
});
await app.listen(process.env.PORT ?? 3000);
```

`ConfigModule.forRoot({ isGlobal: true })` is registered in `AppModule` so `.env` variables (`DATABASE_URL`, `SECRET`, `PORT`) are available anywhere via `ConfigService`.

There is no custom global `ExceptionFilter` wired up. Errors thrown by services (`BadRequestException`, `NotFoundException`, `UnauthorizedException`, `ForbiddenException`, `ConflictException`) travel through Nest's default exception handling and return the standard `{ statusCode, message, error }` envelope. A `src/common/filters/http-exception.filter.ts` file exists in the tree but is empty and is not registered in `main.ts` or through `APP_FILTER`.
