The Milk Distribution ERP backend is a NestJS application written in TypeScript. It exposes a REST API consumed by an Electron desktop client (React \+ Vite) running on distributor workstations. Data is persisted in PostgreSQL through the Prisma ORM. Every HTTP route is protected by JWT authentication and a role-based access control layer.

## Technology Stack

| Layer | Technology | Rationale |
| --- | --- | --- |
| API framework | NestJS (TypeScript) | Opinionated module structure; built-in DI, guards, pipes |
| ORM | Prisma | Type-safe query builder; schema-first migrations |
| Database | PostgreSQL | ACID transactions; well-suited for financial record-keeping |
| Authentication | JWT (Bearer) \+ Passport.js | Stateless; straightforward to validate at the edge |
| Desktop client | Electron \+ React \+ Vite | Native OS integration for offline-capable distribution operations |
| Validation | NestJS `ValidationPipe` (class-validator) | DTO-level input sanitisation before business logic runs |

## Internal Module Layout

Most feature modules follow the same internal layer pattern:

```text
<module>/
├── <module>.controller.ts      # HTTP routes, guards, param parsing
├── <module>.service.ts         # Business logic, orchestration
├── <module>.repository.ts      # Prisma queries
├── <module>-validation.service.ts  # Business-rule validation
├── <module>.builder.ts         # Response/grid construction
├── <module>.constants.ts       # Error messages, config values
├── <module>.module.ts          # NestJS module definition
└── dto/                        # Request body shapes (class-validator)
```

Not every module has every file. Concrete exceptions in the current codebase:

- `auth/` has no builder, validation service, or constants. It ships `auth.controller.ts`, `auth.service.ts`, `auth.repository.ts`, `auth.module.ts`, `auth.guard.ts`, `jwt.strategy.ts`, `roles.guard.ts`, `roles.decorator.ts`, and `dto/`.
- `paper/` has no builder. It also ships `paper.repository.spec.ts` and `paper.service.spec.ts` test files.
- `products/` and `clients/` have no builder and no validation service. `clients/` additionally ships `clients.collections.ts`.
- `delivery-summary/` has no validation service and no `dto/` folder (read-only module).
- `distributor-transfer/` has no `dto/` folder.
- `orders/` uses `order.billing-builder.ts` (not `orders.builder.ts`).
- `trays/` uses `tray.billing-builder.ts` (not `trays.builder.ts`).
- `workflow/` has `workflow-state.service.ts`, `workflow.builder.ts`, `workflow.module.ts`, and `constants/`, `guards/`, `types/` subfolders — no controller or repository.

This separation ensures that HTTP concerns stay in the controller, database concerns stay in the repository, and all domain rules live exclusively in the service and validation service.

## Shared Cross-Cutting Services

Two services are injected into almost every feature module:

- **`WorkflowStateService`** — provides a full set of `canEdit*` boolean methods (`canEditNightEntries`, `canEditMorningEntries`, `canEditNightCollections`, `canEditMorningCollections`, `canEditTrays`, `canEditEmployeeCollections`, `canAdminEditCollections`, `canEditVehicleAllocations`, `canEditPurchases`, `canEditRouteExpenses`, `canEditRouteDenominations`, `canEditDirectCollections`, `canEditBankDeposits`, `canEditDairyTrayTracking`, `canEditDistributorTransfers`, `canFinalize`) plus `validateTransition` for the paper status machine. No module enforces workflow rules independently.
- **`PrismaService`** — the singleton Prisma client (from `src/prisma/prisma.service.ts`); used directly in services for `$transaction` calls and indirectly via repositories for single queries. A separate standalone client in `src/lib/prisma.ts` is used by scripts that need a Prisma instance outside the Nest container.

## Application Bootstrap

`main.ts` creates the NestJS application with a global `ValidationPipe` configured for `whitelist: true` (strips unknown properties) and `transform: true` (auto-converts route params to their declared types):

```typescript
const app = await NestFactory.create(AppModule);
app.useGlobalPipes(
  new ValidationPipe({ whitelist: true, transform: true }),
);
await app.listen(process.env.PORT ?? 3000);
```

There is no custom global `ExceptionFilter` wired up. Errors thrown by services (`BadRequestException`, `NotFoundException`, `UnauthorizedException`, `ForbiddenException`) travel through Nest's default exception handling and return the standard `{ statusCode, message, error }` envelope. A `src/common/filters/http-exception.filter.ts` file exists in the tree but is not registered in `main.ts` or through `APP_FILTER`.
