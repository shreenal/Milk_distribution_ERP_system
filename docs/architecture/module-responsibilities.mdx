Each backend module owns one slice of the domain. Boundaries are defined by which entity the module writes to; multi-entity workflows compose these modules through the shared `WorkflowStateService` rather than crossing directly into another module's tables.

## Module table

| Module | Owns writes to | Key service methods | Depends on |
| --- | --- | --- | --- |
| `auth` | `users` | `AuthService.login`; `AuthController` also exposes `GET /auth/me` which returns `req.user` set by `JwtAuthGuard` | (no domain dependencies) |
| `paper` | `order_paper`, `order_sheet` | `generatePaperService`, `getTodayPaperService`, `getPaperByIdService`, `getPapersService`, `submitNightEntryService`, `submitMorningEntryService`, `finalizePaperService`, `reopenPaperService` | `workflow`, `orders`, `vehicle-allocation`, `trays`, `purchase`, `collections`, `cash-settlement`, `dairy-tray-tracking`, `distributor-transfer` (via readiness validators) |
| `orders` | `order_sheet_items` | `getSheetService`, `getSheetItemsService`, `saveNightEntriesService`, `saveMorningEntriesService` | `workflow`, `products`, `clients` |
| `collections` | `client_collections` | `getCollectionGrid`, `saveNightCollections`, `saveMorningCollections`, `saveAdminCollections` | `workflow` |
| `purchase` | `purchase_paper`, `purchase_entry` | `getPurchases`, `savePurchases` | `workflow`, `products`, `vehicle-allocation` |
| `vehicle-allocation` | `vehicle_allocation_paper`, `vehicle_allocation_entry` | `getVehicleAllocations`, `saveVehicleAllocations` | `workflow` |
| `trays` | `client_tray_transaction` | `getTraySheetService`, `saveTrayEntriesService` | `workflow`, `products` (rule matching) |
| `dairy-tray-tracking` | `dairy_tray_paper` | `getDairyTrayGrid`, `saveDairyTrayEntries` | `workflow`, `trays`, `purchase` |
| `cash-settlement` | `cash_route_expense`, denomination rows, `cash_direct_collection`, `cash_bank_deposit` | `getCashSettlementService`, `saveRouteExpensesService`, `saveRouteDenominationsService`, `saveDirectCollectionsService`, `saveBankDepositsService` | `workflow`, `collections` |
| `distributor-transfer` | `distributor_transfer` | `getTransferSummary`, `generateTransfer` | `workflow`, `orders`, `vehicle-allocation` |
| `delivery-summary` | (read-only) | `getBillingGroupSummary` | `collections`, `orders` |

| `products` | (read-only master data) | `ProductsService` and `ProductsRepository` expose product, rate, and tray-rule lookups | (no domain dependencies) |

## Shared cross-cutting services

Two services are injected across almost every module:

- **`WorkflowStateService`** — pure boolean methods keyed on `PaperStatus`. Every write-side service calls it before mutating; no module implements state gating on its own.
- **`PrismaService`** — the singleton Prisma client, used by services (via `$transaction`) and repositories (via query builders).

One shared repository lives under `common/repositories`:

- **`OrderItemsRepository`** — reused by modules that read order-sheet-item data (for example `orders`, `delivery-summary`, and `distributor-transfer`).

Two shared builders live under `common/builders`:

- **`AllocationSummaryBuilder`** (`allocation-summary.builder.ts`)
- **`ProductColumnsBuilder`** (`product-columns.builder.ts`)

## Why the split matters

- **Feature isolation:** a bug in `cash-settlement` never touches order data.
- **Testability:** each module can be tested against a small set of collaborators.
- **Auditability:** each mutating action lives in exactly one service, so tracing "who wrote this field" is a single search.
