Every route in the Milk Distribution ERP API is protected. There are no public endpoints except the login endpoint itself. Authentication is stateless — the server issues a signed JWT on login and validates it on every subsequent request without hitting the database.

## Token issuance

`POST /auth/login` is the only route that runs without a token. It:

1. Looks up the `users` row by `username` (via `AuthRepository.findUserByUsername`).
2. Compares the supplied password against the stored bcrypt hash with `bcrypt.compare`.
3. On match, signs a JWT with the payload `{ sub: user.id, username, role: user.role.name }`.
4. Returns `{ accessToken, user: { id, username, role } }`.

The signing key is currently hardcoded as `'milk-distribution-secret'` in both `AuthModule` (`JwtModule.register`) and `JwtStrategy`. Tokens expire in `1d` (`signOptions.expiresIn: '1d'`). Moving the secret to `JWT_SECRET` in the environment is a known follow-up.

## Token validation

Every other controller declares `@UseGuards(JwtAuthGuard, RolesGuard)`. The two guards run in order:

1. **`JwtAuthGuard`** — extends `AuthGuard('jwt')` from `@nestjs/passport`. Reads the `Authorization: Bearer <token>` header, verifies the signature and expiry, and attaches `{ id, username, role }` (from `JwtStrategy.validate`) to `request.user`. On failure, throws `UnauthorizedException` (`401`).
2. **`RolesGuard`** — reads the `@Roles(...)` metadata on the handler or class and checks `request.user.role` against a numeric hierarchy: `ADMIN` = 2, `EMPLOYEE` = 1. The check passes when the caller's rank is at least the maximum required. On failure, `canActivate` returns false and Nest emits `403 Forbidden`.

## Roles

Only two roles exist:

| Role | Who | Capabilities |
| --- | --- | --- |
| `EMPLOYEE` | Delivery drivers, route staff, night/morning ops | Read all data, write orders/collections/purchases/trays during the working states |
| `ADMIN` | Supervisors, office managers | Everything an `EMPLOYEE` can do plus finalize, reopen, admin collections, cash settlement |

Roles live in a separate `roles` table (`id`, `name`) referenced from `users.role_id`. The JWT stores the role name string, so `request.user.role` is `'ADMIN'` or `'EMPLOYEE'`. Provisioning happens directly at the database level; there is no user-management endpoint.

## Handler-level enforcement

The `@Roles(...)` decorator narrows access for a specific route. Examples from the codebase:

```typescript
@Post(':paperId/finalize')
@Roles('ADMIN')
async finalizePaper(@Param('paperId', ParseIntPipe) paperId: number) {
  return this.paperService.finalizePaperService(paperId);
}

@Get()
@Roles('EMPLOYEE')
async getPapers(@Query('date') date?: string) {
  return this.paperService.getPapersService(date);
}
```

`@Roles('EMPLOYEE')` implicitly includes `ADMIN` via the `RolesGuard` hierarchy — admins can execute every employee route. The reverse is not true.

## What the token does not do

- **It does not authorize per-record access.** A driver assigned to Route A can read Route B data if they know the sheet ID. Boundary checks like this are not implemented.
- **It does not carry per-page permissions.** All page-level UI gating happens in the client based on `role`.
- **It does not rotate.** There is no refresh endpoint; when the token expires, the client re-authenticates from scratch.
