The API uses a single global exception filter to produce a consistent error envelope regardless of which module threw the error. Clients can parse errors uniformly and surface actionable messages to users without inspecting per-endpoint shapes.

## The error envelope

Every error response — validation, auth, business-rule, or unexpected — is formatted as:

```json
{
  "statusCode": 422,
  "message": "Paper is FINALIZED — reopen to edit",
  "error": "Unprocessable Entity",
  "path": "/orders/sheet/42/morning",
  "timestamp": "2026-07-28T05:30:00.000Z"
}
```

- `statusCode` — HTTP status number.
- `message` — human-readable single sentence.
- `error` — HTTP status text.
- `path` — the URL that failed.
- `timestamp` — ISO8601 server time.

For validation failures the `message` field can be an array of DTO validation strings.

## HttpExceptionFilter

Registered globally in `main.ts`. Every `HttpException` (and subclass) is caught, its status and payload extracted, and the envelope emitted. Non-HTTP exceptions become `500 Internal Server Error` with the same envelope and a redacted message.

The filter is stateless and adds no side effects beyond formatting.

## Custom error base classes

Two thin subclasses live under `common/errors`:

- **`NotFoundError`** → subclass of `NotFoundException`, HTTP 404. Thrown by services when a lookup by ID returns no row.
- **`ValidationError`** → subclass of `UnprocessableEntityException`, HTTP 422. Thrown by `<module>-validation.service.ts` when a business rule fails.

Both preserve the standard `HttpException` interface so `HttpExceptionFilter` handles them without special-casing.

## Client handling guidance

- Show `message` verbatim to the user for `4xx` errors — server messages are already user-facing.
- Show a generic "Something went wrong" for `5xx` responses.
- Log `path` and `timestamp` on every error to correlate with server logs.

All errors in the Milk Distribution ERP backend are ultimately caught and formatted by the global `HttpExceptionFilter`. There is no separate error hierarchy at the HTTP level — both validation errors and business-rule violations throw `BadRequestException` (HTTP 400). The distinction is captured only in the message string.

## `HttpExceptionFilter` Behaviour

The filter is registered globally (configured in the bootstrap function or a global module) and intercepts every unhandled `HttpException` thrown anywhere in the request lifecycle. It is implemented as a NestJS `ExceptionFilter` decorated with `@Catch(HttpException)`. It extracts three pieces of information from the incoming context and exception: the HTTP status code (`exception.getStatus()`), the request URL (`request.url`), and the exception message (`exception.message`). It then calls `response.status(status).json(...)` with a structured body.

When an `HttpException` is caught, the filter extracts the status code, the request path, and the exception message, then writes a uniform JSON response:

```json
{
  "statusCode": 400,
  "timestamp": "2024-11-15T08:23:11.000Z",
  "path": "/orders/sheet/7/night-save",
  "message": "Cannot edit night entries when paper is NIGHT_SUBMITTED. Allowed statuses: DRAFT, REOPENED"
}
```

Unhandled non-`HttpException` errors (e.g., database connection failures) are treated as 500 Internal Server Error; the message is not forwarded to the client in production to avoid leaking internals.

## Error Type Taxonomy

The codebase uses three categories of error:

| Category | How it is thrown | HTTP status | Example |
| --- | --- | --- | --- |
| **DTO validation** | `ValidationPipe` automatically | 400 | `"orderedQty must be a number"` |
| **Business-rule violation** | `throw new BadRequestException(...)` in service | 400 | `"Client 12 does not belong to group 3"` |
| **Not-found** | `throw new BadRequestException(...)` in service | 400 | `"Order paper not found"` (note: 400, not 404) |
| **Auth failure** | `JwtAuthGuard` / `RolesGuard` | 401 / 403 | `"Unauthorized"` / `"Forbidden resource"` |

> **Why 400 for not-found?** The codebase intentionally throws `BadRequestException` (400) for missing records rather than `NotFoundException` (404). This is a deliberate convention — the frontend treats all non-success responses as "something went wrong" and reads the message string rather than branching on status code.

## Validation vs Business-Rule Errors

**DTO validation** (via `class-validator` \+ `ValidationPipe`) fires before the controller method is called. The response shape differs slightly — NestJS produces an array of constraint messages:

```json
{
  "statusCode": 400,
  "message": [
    "orderedQty must be a number conforming to the specified constraints",
    "clientId must be a positive integer"
  ],
  "error": "Bad Request"
}
```

**Business-rule errors** (thrown by services) produce the filter's envelope format with a single string message:

```json
{
  "statusCode": 400,
  "timestamp": "2024-11-15T08:23:11.000Z",
  "path": "/orders/sheet/7/night-save",
  "message": "Client 12 does not belong to group 3"
}
```

The simplest way to distinguish them client-side is to check whether `message` is an array (DTO error) or a string (business-rule error).
