The API relies on NestJS's default exception handling. There is no custom global `ExceptionFilter` registered — the file `src/common/filters/http-exception.filter.ts` exists in the tree but is empty and is not wired into `main.ts` or via an `APP_FILTER` provider. Errors thrown as `BadRequestException`, `NotFoundException`, `UnauthorizedException`, or `ForbiddenException` produce Nest's standard envelope. There is no separate error hierarchy at the HTTP level — both validation errors and business-rule violations throw `BadRequestException` (HTTP 400). The distinction is captured only in the message string.

## Default Nest response shape

Nest's default `HttpException` handling writes a JSON body like:

```json
{
  "statusCode": 400,
  "message": "Cannot edit night entries when paper is NIGHT_SUBMITTED. Allowed statuses: DRAFT, REOPENED",
  "error": "Bad Request"
}
```

- `statusCode` — the HTTP status number.
- `message` — the exception message (or an array of validation strings for DTO failures, see below).
- `error` — the HTTP status text.

There is no `path` or `timestamp` field because no custom filter injects them.

Unhandled non-`HttpException` errors (e.g. database connection failures) fall through to Nest's default `500 Internal Server Error` with `"Internal server error"` as the message.

## Error Type Taxonomy

The codebase uses three categories of error:

| Category | How it is thrown | HTTP status | Example |
| --- | --- | --- | --- |
| **DTO validation** | `ValidationPipe` automatically | 400 | `"orderedQty must be a number"` |
| **Business-rule violation** | `throw new BadRequestException(...)` in a transaction service | 400 | `"Client 12 does not belong to group 3"` |
| **Not-found (transactions)** | `throw new BadRequestException(...)` in most transaction services | 400 | `"Order paper not found"` (note: 400, not 404) |
| **Not-found (masters \+ distributor-transfer \+ client-trays \+ dairy-trays)** | `throw new NotFoundException(...)` in a master or in `DistributorTransferService`, `ClientTraysService`, or `DairyTraysService` | 404 | `"Client not found"`, `"Order paper not found"`, `"Sheet not found"` |
| **Duplicate unique key (masters)** | `throw new ConflictException(...)` in a master service | 409 | `"Username already exists"`, `"Tray type already exists for this brand and color"` |
| **Auth failure** | `JwtAuthGuard` / `RolesGuard` | 401 / 403 | `"Unauthorized"` / `"Forbidden resource"` |

> **Why the split?** Most transaction services (`paper`, `orders`, `collections`, `purchase`, `vehicle-allocation`, `cash-settlement`, `delivery-summary`) throw `BadRequestException` for missing rows so the frontend can treat every non-success response uniformly. Master services (`src/modules/masters/*`) follow the CRUD idiom and use `NotFoundException` (404) for missing rows and `ConflictException` (409) for duplicate unique keys. Three transaction services use `NotFoundException` for missing top-level entities: `DistributorTransferService` (missing paper), `ClientTraysService` (missing sheet), and `DairyTraysService` (missing paper). Their business-rule violations still use `BadRequestException` like every other transaction service.

## Error Messages by Module

Each module defines its error messages as constants in a `<module>.constants.ts` file. This makes messages easy to locate and test.

### Paper module (`paper.constants.ts`)

The exported constant is `ERROR_MESSAGES` (paired with `SUCCESS_MESSAGES` and a `DATE_CONFIG` object holding `MAX_FUTURE_DAYS: 30` and `TIMEZONE: 'Asia/Kolkata'`).

```typescript
INVALID_PAPER_ID: 'Invalid paper ID provided'
PAPER_NOT_FOUND: 'Order paper not found'
NO_PAPERS_FOUND: 'No papers found in system'
NO_ACTIVE_GROUPS: 'No active groups found to generate sheets'
INVALID_STATUS_TRANSITION: (current, target) =>
  `Cannot transition from ${current} to ${target}`
MUST_RESUBMIT_MORNING: (previousStatus) =>
  `After reopening from ${previousStatus}, you must resubmit morning entry before finalizing`
INVALID_DATE_FORMAT: 'Invalid date format'
PAST_DATE_NOT_ALLOWED: 'Cannot perform operations on past dates'
FUTURE_DATE_TOO_FAR: (maxDays) => `Cannot generate paper more than ${maxDays} days ahead`
PAPER_NOT_IN_DRAFT_STATUS: 'Paper not in DRAFT status'
MISSING_REQUIRED_FIELD: (field) => `Required field "${field}" is missing`
```

  `Product ${productId} does not belong to group ${groupId}`

  `Client ${clientId} does not belong to group ${groupId}`

  `No orders entered for sheet "${groupName}". Please enter at least one order before submitting.`

## Common Error Scenarios

| Scenario | Module | Typical message |
| --- | --- | --- |
| Token missing | Auth guard | `"Unauthorized"` (401) |
| Insufficient role | Roles guard | `"Forbidden resource"` (403) |
| Paper already exists for date | Paper | Returns existing paper (not an error) |
| Paper date is in the past | Paper | `"Cannot perform operations on past dates"` |
| Paper date \> 30 days ahead | Paper | `"Cannot generate paper more than 30 days ahead"` |
| Paper not in expected status | Workflow | `"Cannot transition from DRAFT to FINALIZED"` |
| Night entries when status ≠ DRAFT | Orders | `"Cannot edit night entries when paper is NIGHT_SUBMITTED..."` |
| Duplicate client\+product in request | Orders | `"Duplicate entries found: 12_5, ..."` |
| No rate configured for product/date | Orders | `"No active rate found for product 5 on date 2024-11-15T00:00:00.000Z"` |
| Morning entry without prior night entry | Orders | `"No ordered quantity found for Client 12, Product 5"` |
| Client not in sheet's group | Orders | `"Client 12 does not belong to group 3"` |
| Admin collection outside allowed status | Collections | `"Admin collections cannot be edited in current workflow state"` |
| Vehicle not assigned to a distributor | Vehicle allocation | _(from constants)_ |
| No vehicle allocations for paper | Purchase | `"No vehicle allocations found for this paper"` |

## Validation vs Business-Rule Errors

**DTO validation** (via `class-validator` \+ `ValidationPipe`) fires before the controller method is called. The response shape differs slightly — NestJS produces an array of constraint messages:

```json
{
  "statusCode": 400,
  "message": [
    "orderedQty must be a number conforming to the specified constraints",
    "clientId must be a positive integer"
  ],
  "error": "Bad Request"
}
```

**Business-rule errors** (thrown by services) use Nest's default envelope with a single string message:

```json
{
  "statusCode": 400,
  "message": "Client 12 does not belong to group 3",
  "error": "Bad Request"
}
```

The simplest way to distinguish them client-side is to check whether `message` is an array (DTO error) or a string (business-rule error).
