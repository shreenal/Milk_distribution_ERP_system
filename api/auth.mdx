The Authentication module is the gateway to every other part of the system. Before a route driver, office operator, or admin can read or write any data, they must obtain a JSON Web Token by logging in. That token is then sent as a `Bearer` header on every subsequent request. There are exactly two roles in the system: **EMPLOYEE** (drivers, operators, data-entry staff) and **ADMIN** (supervisors who can finalize or reopen papers and record office-side collection data). The two endpoints below cover the full authentication surface — login and identity verification.

---

## POST /auth/login

### Purpose

Exchanges a username and password for a short-lived JWT access token. This is the only endpoint that does **not** require an existing token. Every client session — whether a mobile handset on a delivery route or the office desktop — starts here.

### When it is called

Called once at the start of every work session. A typical workflow is: the employee opens the app → the app calls `/auth/login` → stores the returned `accessToken` in secure local storage → attaches it as `Authorization: Bearer <token>` on all later calls. The token is re-used until it expires, at which point the client calls this endpoint again.

### Request body

<ParamField body="username" type="string" required>
  The operator's unique username, as provisioned by the system administrator. Case-sensitive.
</ParamField>

<ParamField body="password" type="string" required>
  The operator's plaintext password. Transmitted over HTTPS; hashed server-side before comparison.
</ParamField>

#### Example request

```json
POST /auth/login
Content-Type: application/json

{
  "username": "route_driver_01",
  "password": "SecurePass@2024"
}
```

### Response

On success the server returns HTTP **200** with the following body:

<ResponseField name="accessToken" type="string">
  A signed JWT. Include this value in the `Authorization: Bearer <accessToken>` header on every authenticated request. Treat it like a password — do not log or expose it.
</ResponseField>

<ResponseField name="user" type="object">
  Identity summary of the authenticated user.

  <Expandable title="user fields">
    <ResponseField name="id" type="number">
      Numeric primary key of the user record.
    </ResponseField>

    <ResponseField name="username" type="string">
      The username that was used to authenticate.
    </ResponseField>

    <ResponseField name="role" type="string">
      Either `EMPLOYEE` or `ADMIN`. Controls which operations the token may authorise.
    </ResponseField>
  </Expandable>
</ResponseField>

#### Example response

```json
HTTP/1.1 200 OK
Content-Type: application/json

{
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOjQsInVzZXJuYW1lIjoicm91dGVfZHJpdmVyXzAxIiwicm9sZSI6IkVNUExPWUVFIiwiaWF0IjoxNzE1MDAwMDAwLCJleHAiOjE3MTUwODY0MDB9.SIGNATURE",
  "user": {
    "id": 4,
    "username": "route_driver_01",
    "role": "EMPLOYEE"
  }
}
```

### Validation and errors

| Scenario | HTTP status | Detail |
| --- | --- | --- |
| Missing `username` or `password` field | `400 Bad Request` | Validation error listing the missing fields |
| Incorrect username or password | `401 Unauthorized` | Generic "Invalid credentials" message (no hint about which field is wrong) |
| Account does not exist | `401 Unauthorized` | Same generic response — the system does not reveal whether the username exists |

### Related endpoints

- `GET /auth/me` — verify that a stored token is still valid and retrieve the associated role
- All other endpoints — require the `accessToken` returned here

## GET /auth/me

### Purpose

Returns the identity embedded in the current JWT without issuing a new token. Use this to confirm that a token is still valid, to read the caller's role at runtime, or to bootstrap a client UI that needs to know whether to show admin-only controls.

### When it is called

Called immediately after login to populate the client's session state, and optionally on each app start to verify that a cached token has not expired. It is also useful during development to confirm that the correct role is being served.

### Request headers

<ParamField header="Authorization" type="string" required>
  Must be `Bearer <accessToken>` where `<accessToken>` is the JWT obtained from `POST /auth/login`.
</ParamField>

#### Example request

```http
GET /auth/me
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

### Response

Returns the decoded user payload from the token. No database look-up is performed; the data comes directly from the JWT claims.

<ResponseField name="id" type="number">
  The numeric user ID embedded in the token.
</ResponseField>

<ResponseField name="username" type="string">
  The username embedded in the token.
</ResponseField>

<ResponseField name="role" type="string">
  The role claim in the token — `EMPLOYEE` or `ADMIN`.
</ResponseField>

#### Example response

```json
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 4,
  "username": "route_driver_01",
  "role": "EMPLOYEE"
}
```

### Validation and errors

| Scenario | HTTP status | Detail |
| --- | --- | --- |
| `Authorization` header absent | `401 Unauthorized` | No token provided |
| Token malformed or tampered with | `401 Unauthorized` | JWT verification failed |
| Token expired | `401 Unauthorized` | Token has passed its expiry time; re-authenticate via `POST /auth/login` |
| Wrong scheme (e.g. `Basic` instead of `Bearer`) | `401 Unauthorized` | Unsupported authentication scheme |

### Related endpoints

- `POST /auth/login` — obtain a token before calling this endpoint
